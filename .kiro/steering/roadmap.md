# Roadmap

> updated_at: 2026-10-13（`/kiro-discovery` で予選 10/31 に向けた進め方を決定）

## Overview

予選（2026-10-31）までに、審査員が触って価値が分かる状態にする。審査員が自分のアカウントで初回から触る場合と、こちらがデモで開き直す場合の両方があり得る。そのため、次の3つを10/31までにそろえる。

- 初回の人が迷わず時間割を確定できること
- 保存した時間割が消えないこと
- 空きコマ検索という新しい価値が見えること

進め方は、まず `src/` を目標の構成（`structure.md`「目標の構成（2026-10-13 決定）」）へ**完全に**移行する。そのうえで不具合修正 → 空きコマ検索 → UI 見直し（最重要画面のみ）の順に、1つずつ spec を進める。実装は一人（＋Claude）で、spec を同時に進めない。

## Approach Decision

- **Chosen**: 案B「移行をやり切ってから、ほかに進む」
  - 全ファイルを目標の構成に移す
  - 全画面の計算・通信を `hooks/`・`utils/`・`services/` に出しきる
  - そのうえで後続の spec を進める
- **Why**:
  - 後続の spec（不具合修正・空きコマ検索・UI）がすべて、ルールどおりの構成の上で作業できる
  - 画面に重複している計算（学期・クォーターの判定、セル探し、受講できる科目の絞り込み、合格の判定）が1か所にまとまる。修正漏れが起きにくい
- **Rejected alternatives**:
  - 案A「移行の範囲を絞って最初にやる」（画面ごとのロジックは UI の spec で出す）：UI の時間は多く取れる。ただし、移行が終わっても画面に計算が残り、構成がルールに沿わない期間が続くため見送り
  - 案C「移行は予選の後」：新しいコードを後で全部移すことになり、手戻りが最も大きいため見送り
- **トレードオフ（受け入れたもの）**: UI 見直しに使えるのは約4日。そのため UI は最重要の画面（3 科目選択・5 生成）だけを作り直し、ほかの画面は小さな改善にとどめる

## Scope

- **In（10/31 まで）**:
  - `src/` の目標の構成への完全移行（見た目・動きは変えない。lint エラーをゼロにする）
  - 既知の不具合の修正：
    - 5限より後の時限が表示されない
    - ピン留めしたクラスが AI に渡っていない
    - Firestore の同期の問題
    - 合格の判定が4か所でばらばら
  - 空きコマ検索（画面5 生成のプレビューで使う）
  - UI 見直し：画面の流れ（1〜8）は保つ。画面3・5を作り直し、ほかは説明文などの小さな改善
- **Out（予選の後に回す）**:
  - シラバスと口コミの DB 化（予選までは今の JSON のまま）
  - 全国展開
  - 画面の流れの変更（画面の追加・統合・並べ替え）
  - ダッシュボード（6）・成績入力（7）の作り直し
  - `api/*` の認証（Firebase ID トークンの検証）
  - `firestore.rules` のリポジトリ管理
  - `@google/genai` への移行、モデル名の変更
  - 未使用のコードや機能を残すか消すかの決定（ReflectionScreen、`/api/chatbot`、再履修モード、通年、教室名、モック生成、ビット計算関数）
  - 卒業要件の計算
  - テストの導入

## Constraints

- 期限：2026-10-31（予選）。今日は 2026-10-13
- 体制：一人（＋Claude）。spec は1つずつ順番に進め、同時に進めない
- 目安の日程：

  | spec | 期間 |
  |------|------|
  | 移行 | 10/14〜10/19 |
  | 不具合修正 | 〜10/22 |
  | 空きコマ検索 | 〜10/26 |
  | UI | 〜10/30 |

  遅れたときは UI の範囲を削る
- シラバス・口コミは `src/data/*.json` のまま使う
- 新しいライブラリは入れない
- 型の正は `data-model.md`。データの形を変える spec は、先に `data-model.md` を直す
- 秘密情報をコード・commit に入れない。Gemini は必ず `api/` から呼ぶ
- `product.md` の「現状の位置づけ」にある未使用のコードや機能は、勝手に使い始めたり消したりしない
- 新しく作る機能は「会津大学専用」の作りにしすぎない（`product.md`）
- 各 spec の実装が終わったら、変わった仕様を `.kiro/steering/` に反映する

## Boundary Strategy

- **Why this split**:
  - 「動きを変えない移行」と「動きを変える修正」を別の spec にする。こうすると、移行のレビューは「見た目と動きが同じか」だけを確かめればよい
  - 不具合修正を空きコマ検索より先に置く。5限より後が表示されないままだと「空いているコマ」の判定自体が誤り、合格の判定がばらばらだと修得済み科目を正しく除けないため
  - UI を最後に置く。画面5は空きコマ検索の入口も含めて一度に作り直せるし、時間が足りなければ UI の範囲だけを削ればよい
- **Shared seams to watch**:
  - **移行 ↔ 不具合修正**：移行では既知の不具合もそのまま残す。例：`maxPeriods` の初期値 5、ピンを送らない、読み込み前の書き込み。直すのは `core-bug-fixes` で行う
  - **移行で作る部品の形**：移行で切り出す `utils/`（学期・クォーターの判定、セル探し、受講できる科目の絞り込み、合格の判定）、`hooks/`（Firestore 同期など）、`services/aiApi.ts` の形は、後続の3つの spec が全部使う。名前と引数は移行の design で決める
  - **不具合修正 ↔ data-model.md**：ピンを AI に送ると `TimetablePatternsRequest` の形が変わる。先に `data-model.md` を直す
  - **空きコマ検索 ↔ UI**：どちらも画面5（`GeneratorScreen`）を触る。空きコマ検索は「検索と追加の仕組みと、最低限の UI」を持つ。見た目の作り直しは UI の spec が持つ
  - **空きコマ検索 ↔ 時限の表示**：「空き」の判定は、`core-bug-fixes` で直した時限の範囲（何限まで見るか）と、クォーター（奇数Q・偶数Q）の分け方に従う
