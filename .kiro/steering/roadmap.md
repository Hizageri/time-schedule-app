# Roadmap

> updated_at: 2026-10-22（`/kiro-discovery` で見直し。同日、ユーザーデータの持ち方（大学 ID・年度つきの科目 ID）を `university-data-model` に追記。予選（10/31）は通過しなかったため、目標を「インターン先への提出」と「全国展開を前提にした設計」に変えた）
> 前の版（2026-10-13、予選に向けた計画）は git の履歴に残っている

## Overview

目標は2つあり、この順番で優先する。

1. **安全で、正常に動くこと**（最優先）：約1週間後（2026-10-29 ごろ）にインターン先へ提出する。提出時点で、安全面の穴がなく、保存したデータが消えない状態にする
2. **全国展開を前提にした設計にすること**：会津大学だけで使う場合に楽なやり方があっても、「全国の大学で使うにはどうするか」を基準に選ぶ

進め方は2段階に分ける。第1段階（提出まで）は、安全性の対応と既知の不具合の修正を1つの spec（`secure-and-stable`）にまとめ、今のフォルダ構成のまま直す。第2段階（提出の後）は、フォルダ構成の移行 → 全国展開向けのデータ設計 → シラバス・口コミの DB 化 → 空きコマ検索 → UI の作り直し、の順に1つずつ spec を進める。実装は一人（＋Claude）で、spec を同時に進めない。テストがないため、各 spec の決まった段階で手による確認（下の「確認の方法」）を行う。

## Approach Decision

- **Chosen**: 案A「2段階に分ける」
  - 第1段階（〜10/29）：`secure-and-stable`（安全性＋不具合修正）を、今の構成のまま行う
  - 第2段階（提出後）：移行 → 全国展開向けのデータ設計 → DB 化 → 空きコマ検索 → UI
- **Why**:
  - 1週間で「安全・正常に動く」を確実に終えられる。前の計画では移行だけで4〜6日かかる見込みだった
  - 提出先が最初に気にするのは、安全面とデータが消えないこと。見た目の作り込みはその後でよい
  - 全国展開向けのデータ設計を、空きコマ検索や UI より先に置く。後から作る機能が会津大学専用の前提に乗らずに済む
- **Rejected alternatives**:
  - 案B「前の計画どおり移行から始める」：構成はきれいになるが、1週間では移行で終わる可能性が高い。提出時に安全性の穴とデータが消える不具合が残るため見送り
  - 案C「第1段階は安全性だけにする」：確実に間に合うが、データが消える不具合が残り、「正常に動く」を満たさないため見送り
  - 前の版の案B（2026-10-13、予選に向けて移行を先に行う）：予選がなくなり、優先順位が変わったため置きかえた
- **トレードオフ（受け入れたもの）**:
  - 第1段階は移行前の構成で直すので、第2段階の移行で、直した場所をもう一度動かす。手戻りを小さくするため、第1段階で新しく書く判定や計算は、移行先（`utils/` など）にそのまま移せる形にする

## Scope

- **In（第1段階：〜10/29）**:
  - `api/*` の認証（Firebase ID トークンの検証）と入力チェック
  - Firestore のセキュリティルールのリポジトリ管理と確認
  - 依存パッケージの脆弱性の解消（`npm audit fix`、`--force` は使わない）、本番に残るデバッグ用ログの削除
  - 既知の不具合の修正：
    - ログイン直後に保存した状態が初期値で上書きされる（データが消える）
    - 消したデータがリロードで戻る、別の科目までまとめて消える
    - 6限より後の時限が表示されない
    - ピン留めしたクラスが AI に渡っていない
    - 合格の判定が4か所でばらばら
- **In（第2段階：提出後）**:
  - `src/` の目標の構成への移行（見た目・動きは変えない）
  - 全国展開向けのデータ設計（大学ごとの学期制・時限・成績の段階・科目の条件を、設定として持てるようにする）
  - シラバスと口コミの DB 化
  - 空きコマ検索（画面5 生成のプレビューで使う）
  - UI の作り直し（画面3・5）と、ほかの画面の小さな改善
- **Out（今のロードマップでは扱わない）**:
  - 会津大学以外の大学のデータを実際に集めて入れること（第2段階で、入れられる仕組みまでを作る）
  - 画面の流れの変更（画面の追加・統合・並べ替え）
  - ダッシュボード（6）・成績入力（7）の作り直し
  - `@google/genai` への移行、モデル名の変更
  - 未使用のコードや機能を残すか消すかの決定（ReflectionScreen、`/api/chatbot`、再履修モード、通年、教室名、モック生成、ビット計算関数）
  - 卒業要件の計算
  - PHP を使うこと（方針として使わない。`tech.md`）

## Constraints

- 期限：第1段階はインターン先への提出（2026-10-29 ごろ）。今日は 2026-10-22。第2段階に期限はない
- 体制：一人（＋Claude）。spec は1つずつ順番に進め、同時に進めない
- 第1段階の目安の日程：

  | 作業 | 期間 |
  |------|------|
  | `secure-and-stable` の requirements・design・tasks | 10/22〜10/23 |
  | 実装：安全性 | 10/23〜10/25 |
  | 実装：データが消える不具合 | 10/25〜10/26 |
  | 実装：そのほかの不具合 | 10/26〜10/27 |
  | 本番 URL での確認・直し | 10/28 |
  | 提出 | 10/29 ごろ |

- 第1段階で遅れたときに削る順番（安全性とデータが消える不具合は削らない）：
  1. ピン留めの AI への反映
  2. 合格の判定の統一
  3. 6限より後の時限の表示
- **全国展開を前提にする**：新しく書くものは、大学名・学期制（4学期制）・成績の段階（A〜F）・時限の数（11限）・科目の条件のビットの意味を決め打ちにしない。今の値は1か所の設定や引数から渡す。会津大学専用のほうが楽な場面でも、全国展開で困らないほうを選ぶ
- 第2段階に入るまでは、シラバス・口コミは `src/data/*.json` のまま使う
- 新しいライブラリはなるべく入れない。入れるときは design で理由を書く
- PHP は使わない
- 型の正は `data-model.md`。データの形を変える spec は、先に `data-model.md` を直す
- 秘密情報をコード・commit に入れない。Gemini は必ず `api/` から呼ぶ
- `product.md` の「現状の位置づけ」にある未使用のコードや機能は、勝手に使い始めたり消したりしない
- Firebase・Vercel の管理画面での作業は作者が行う。手順を書いて渡す
- 各 spec の実装が終わったら、変わった仕様を `.kiro/steering/` に反映する

## 確認の方法

テストがないので、決まった段階で手で確認する。確認は `npm run dev`（ローカル）で行い、spec の最後の1回は本番 URL で行う。

### 共通の確認（流れの確認）

毎回、次の2つのアカウントで行う。

- **新しいアカウント**：Firestore にデータがない状態から始める
- **使ったことのあるアカウント**：時間割を確定済みの状態から始める

| # | 段階 | 確認すること |
|---|------|--------------|
| 1 | ログイン | ・Google でログインできる<br>・新しいアカウントはオンボーディング（1）、使ったことのあるアカウントはダッシュボード（6）に進む<br>・ログイン直後に、保存した時間割が初期値に戻っていない |
| 2 | 条件・科目選択（2・3） | ・学年・学期・ベースクラスを選ぶと、合う科目だけが出る<br>・詳細モーダルが開き、シラバス・口コミ・成績評価割合が出る<br>・ピン留めできる<br>・選んだ単位数が合う |
| 3 | AI 相談（4） | ・全体講評と科目ごとのコメントが出る。失敗したときは代わりの文面が出る<br>・スキップして進める |
| 4 | 時間割作成（5） | ・5パターンが出る<br>・Q 切替、重なりの赤表示、クラスの手動変更、一時退避ができる<br>・確定するとダッシュボード（6）に時間割が出る |
| 5 | 成績入力（7） | ・成績を入れるとコマどり先輩の反応が出る<br>・GPA が合う<br>・「新学期へ進む」で学期（と学年）が進み、条件（2）に戻る |
| 6 | 保存 | ・どの段階でもリロードして、状態が保たれている（時間割・成績・ピン） |

あわせて、毎回 `npm run build` が通ることを確かめる。

## Boundary Strategy

- **Why this split**:
  - 第1段階を1つの spec にまとめる。提出までの1週間で、spec の行き来の手間を減らす
  - 第2段階では「動きを変えない移行」を最初に置く。移行のレビューは「見た目と動きが同じか」だけを確かめればよい
  - 全国展開向けのデータ設計を、DB 化・空きコマ検索・UI より先に置く。DB の形も、空きコマの判定も、UI の表示も、大学ごとの設定を前提に作れる
  - UI を最後に置く。画面5は空きコマ検索の入口も含めて一度に作り直せる
- **Shared seams to watch**:
  - **`secure-and-stable` ↔ `src-structure-migration`**：第1段階で直した同期の処理・合格の判定・API の呼び出し（ID トークン付き）を、移行で目標の構成に移す。移行では動きを変えない
  - **`secure-and-stable` ↔ `university-data-model`**：第1段階で設定や引数に出した「大学ごとに変わる値」（時限の数、成績の段階、学期制など）を、大学ごとの設定に置きかえる
  - **`secure-and-stable` ↔ data-model.md**：ピンを AI に送ると `TimetablePatternsRequest` の形が変わる。API に ID トークンを送る形も決める。先に `data-model.md` を直す
  - **`university-data-model` ↔ `syllabus-db`**：DB の形は、大学ごとの設定とシラバスの形（`data-model.md`）に従う。科目 ID（大学・年度・科目コード）の付け方は `university-data-model` で決め、`syllabus-db` はその ID で科目を引けるようにする。過去の学期の科目も引けるよう、シラバスは年度ごとに残す
  - **移行で作る部品の形**：`utils/`（学期・クォーターの判定、セル探し、受講できる科目の絞り込み、合格の判定）、`hooks/`（Firestore 同期など）、`services/aiApi.ts` の形は、後続の spec が使う。名前と引数は移行の design で決める
  - **`course-history` ↔ `university-data-model`**：取った科目の登録は、学期ごとの保存の形と年度つきの科目 ID の上に作る。先に形を決めてから作る
  - **空きコマ検索 ↔ UI**：どちらも画面5（`GeneratorScreen`）を触る。空きコマ検索は「検索と追加の仕組みと、最低限の UI」を持つ。見た目の作り直しは UI の spec が持つ
  - **空きコマ検索 ↔ 時限の表示**：「空き」の判定は、`secure-and-stable` で直した時限の範囲と、クォーターの分け方に従う

## Specs (dependency order)

### 第1段階（〜2026-10-29）

- [ ] secure-and-stable -- `api/*` の認証と入力チェック、Firestore のルール、依存パッケージとログの整理（安全性）と、Firestore 同期・6限より後の表示・ピン留めの反映・合格の判定の統一（不具合修正）。今の構成のまま直す。Dependencies: none

### 第2段階（提出の後）

- [ ] src-structure-migration -- `src/` を目標の構成へ移行する。必須はフォルダの移動と、後続の spec が使う部品（utils/・hooks/・services/aiApi.ts）の切り出し。余裕があれば lint ゼロと、それ以外の画面の整理。見た目と動きは変えない。Dependencies: secure-and-stable
- [ ] university-data-model -- 学期制・時限の数・成績の段階・科目の条件（target_bit の意味）・大学名を、大学ごとの設定として持てるようにする。会津大学は設定の1つになる。あわせてユーザーデータを次の形にする：①大学は名前（`"会津大学"`）ではなく大学 ID（例：`universityId: "u-aizu"`）で持ち、名前は大学の設定から引く ②選んだ科目はシラバスの中身を丸ごとコピーせず、年度つきの科目 ID（例：`"u-aizu/2026/HS01"`）だけを持つ。中身は ID から引く（`syllabus-db` までは `src/data/*.json` から引く）③学期ごとに保存する場所を分け（例：`users/{uid}/terms/{学期ID}`）、「新学期へ進む」で前の学期の時間割・成績を消さずに履歴として残す。今のユーザーのデータの移し替えも行う。Dependencies: src-structure-migration
- [ ] syllabus-db -- シラバスと口コミを `src/data/*.json` から DB に移し、大学ごとに持てるようにする。Dependencies: university-data-model
- [ ] course-history -- アプリを使う前に取った科目を、オンボーディング（あとからプロフィールでも）で登録できるようにする。登録した科目は合格済みとして扱い、科目選択にも時間割作成にも出さない。登録は「過去の学期の記録」として、`university-data-model` で決めた学期ごとの形で保存する。合格の判定は `isCoursePassed`（2026-10-22 に作成）を使う。Dependencies: university-data-model
- [ ] empty-slot-search -- 画面5のプレビューで、空いているコマに入れられる科目（学年・学期に合い、修得済みでないもの）を探して追加できるようにする。Dependencies: secure-and-stable, src-structure-migration, university-data-model
- [ ] first-run-ux-refresh -- 画面の流れは保ったまま、画面3（科目選択）と画面5（生成）を初めての人でも迷わない形に作り直す。ほかの画面は説明文などの小さな改善にとどめる。Dependencies: src-structure-migration, empty-slot-search

`university-data-model`・`syllabus-db`・`course-history` の brief は、着手するときに作る。`src-structure-migration`・`empty-slot-search`・`first-run-ux-refresh` の brief は予選に向けて書いたものなので、着手するときにこのロードマップに合わせて見直す。
