# Roadmap

> updated_at: 2026-10-13（`/kiro-discovery` で予選 10/31 に向けた進め方を決定）

## Overview

予選（2026-10-31）までに、審査員が触って価値が分かる状態にする。審査員が自分のアカウントで初回から触る場合と、こちらがデモで開き直す場合の両方があり得る。そのため、次の3つを10/31までにそろえる。

- 初回の人が迷わず時間割を確定できること
- 保存した時間割が消えないこと
- 空きコマ検索という新しい価値が見えること

進め方は、まず `src/` を目標の構成（`structure.md`「目標の構成（2026-10-13 決定）」）へ移行する。移行は「必須」と「余裕があれば」に分け、必須を終えたら次へ進む。そのうえで不具合修正 → 空きコマ検索 → UI 見直し（最重要画面のみ）の順に、1つずつ spec を進める。実装は一人（＋Claude）で、spec を同時に進めない。テストがないため、各 spec の決まった段階で手による確認（下の「確認の方法」）を行う。

## Approach Decision

- **Chosen**: 案B「移行をやり切ってから、ほかに進む」を、範囲を「必須」と「余裕があれば」に分けて進める
  - **必須**：
    - フォルダの移動（`structure.md`「現状からの対応」の表のすべて）
    - 後続の spec が使う部品の切り出し（`utils/`・`hooks/`・`services/aiApi.ts`）
  - **余裕があれば**：
    - lint エラーをゼロにする
    - 必須以外の画面の整理（後続の spec が使わないロジックを、画面から `hooks/` に出す）
  - 必須を終えたら後続の spec に進む。余裕があれば部分は、日程に余裕があるときだけ行う
  - 範囲を分ける理由：テストがない中で6日で全部やると、動きを壊したまま気づかずに進むおそれがある
- **Why**:
  - 後続の spec（不具合修正・空きコマ検索・UI）がすべて、ルールどおりの構成の上で作業できる
  - 画面に重複している計算（学期・クォーターの判定、セル探し、受講できる科目の絞り込み、合格の判定）が1か所にまとまる。修正漏れが起きにくい
- **Rejected alternatives**:
  - 案A「移行の範囲を絞って最初にやる」（画面ごとのロジックは UI の spec で出す）：UI の時間は多く取れる。ただし、移行が終わっても画面に計算が残り、構成がルールに沿わない期間が続くため見送り
  - 案C「移行は予選の後」：新しいコードを後で全部移すことになり、手戻りが最も大きいため見送り
- **トレードオフ（受け入れたもの）**:
  - UI 見直しに使えるのは約4日。そのため UI は最重要の画面（3 科目選択・5 生成）だけを作り直し、ほかの画面は小さな改善にとどめる
  - 移行の「余裕があれば」部分は、予選までに終わらない可能性がある。その場合は予選の後に続ける

## Scope

- **In（10/31 まで）**:
  - `src/` の目標の構成への移行（見た目・動きは変えない）
    - 必須：フォルダの移動、後続の spec が使う部品（`utils/`・`hooks/`・`services/aiApi.ts`）の切り出し
    - 余裕があれば：lint エラーをゼロにする、必須以外の画面の整理
  - 既知の不具合の修正：
    - 5限より後の時限が表示されない
    - ピン留めしたクラスが AI に渡っていない
    - Firestore の同期の問題
    - 合格の判定が4か所でばらばら
  - 空きコマ検索（画面5 生成のプレビューで使う）
  - UI 見直し：画面の流れ（1〜8）は保つ。画面3・5を作り直し、ほかは説明文などの小さな改善
- **Out（予選の後に回す）**:
  - シラバスと口コミの DB 化（予選までは今の JSON のまま）
  - 全国展開
  - 画面の流れの変更（画面の追加・統合・並べ替え）
  - ダッシュボード（6）・成績入力（7）の作り直し
  - `api/*` の認証（Firebase ID トークンの検証）
  - `firestore.rules` のリポジトリ管理
  - `@google/genai` への移行、モデル名の変更
  - 未使用のコードや機能を残すか消すかの決定（ReflectionScreen、`/api/chatbot`、再履修モード、通年、教室名、モック生成、ビット計算関数）
  - 卒業要件の計算
  - テストの導入

## Constraints

- 期限：2026-10-31（予選）。今日は 2026-10-13
- 体制：一人（＋Claude）。spec は1つずつ順番に進め、同時に進めない
- 目安の日程：

  | spec | 期間 |
  |------|------|
  | 移行（必須） | 10/14〜10/17 |
  | 移行（余裕があれば） | 10/18〜10/19（余裕があるときだけ） |
  | 不具合修正 | 〜10/22 |
  | 空きコマ検索 | 〜10/26 |
  | UI | 〜10/30 |

- 遅れたときに削る順番（審査員が一番目にするのは UI なので、UI の時間を最後まで守る）：
  1. 移行の「余裕があれば」部分
     1. 必須以外の画面の整理
     2. lint エラーをゼロにする
  2. UI の範囲（ここまで削っても足りないときだけ）
     1. ログイン・画面1・2・4 の小さな改善
     2. 画面3（科目選択）の作り直し（説明文の改善にとどめる）
     3. 画面5（生成）の作り直しは最後まで残す
- 移行の「必須」、不具合修正、空きコマ検索は削らない。遅れたら上の順で時間を空けて充てる
- シラバス・口コミは `src/data/*.json` のまま使う
- 新しいライブラリは入れない
- 型の正は `data-model.md`。データの形を変える spec は、先に `data-model.md` を直す
- 秘密情報をコード・commit に入れない。Gemini は必ず `api/` から呼ぶ
- `product.md` の「現状の位置づけ」にある未使用のコードや機能は、勝手に使い始めたり消したりしない
- 新しく作る機能は「会津大学専用」の作りにしすぎない（`product.md`）
- 各 spec の実装が終わったら、変わった仕様を `.kiro/steering/` に反映する

## 確認の方法

テストがないので、決まった段階で手で確認する。確認は `npm run dev`（ローカル）で行い、最後の1回だけ本番 URL で行う。

### 共通の確認（流れの確認）

毎回、次の2つのアカウントで行う。

- **新しいアカウント**：Firestore にデータがない状態から始める
- **使ったことのあるアカウント**：時間割を確定済みの状態から始める

| # | 段階 | 確認すること |
|---|------|--------------|
| 1 | ログイン | ・Google でログインできる<br>・新しいアカウントはオンボーディング（1）、使ったことのあるアカウントはダッシュボード（6）に進む<br>・ログイン直後に、保存した時間割が初期値に戻っていない |
| 2 | 条件・科目選択（2・3） | ・学年・学期・ベースクラスを選ぶと、合う科目だけが出る<br>・詳細モーダルが開き、シラバス・口コミ・成績評価割合が出る<br>・ピン留めできる<br>・選んだ単位数が合う |
| 3 | AI 相談（4） | ・全体講評と科目ごとのコメントが出る。失敗したときは代わりの文面が出る<br>・スキップして進める |
| 4 | 時間割作成（5） | ・5パターンが出る<br>・Q 切替、重なりの赤表示、クラスの手動変更、一時退避ができる<br>・確定するとダッシュボード（6）に時間割が出る |
| 5 | 成績入力（7） | ・成績を入れるとコマどり先輩の反応が出る<br>・GPA が合う<br>・「新学期へ進む」で学期（と学年）が進み、条件（2）に戻る |
| 6 | 保存 | ・どの段階でもリロードして、状態が保たれている（時間割・成績・ピン） |

あわせて、毎回 `npm run build` が通ることを確かめる。lint は、移行の「余裕があれば」部分でゼロにした後からは毎回確かめる。

## Boundary Strategy

- **Why this split**:
  - 「動きを変えない移行」と「動きを変える修正」を別の spec にする。こうすると、移行のレビューは「見た目と動きが同じか」だけを確かめればよい
  - 不具合修正を空きコマ検索より先に置く。5限より後が表示されないままだと「空いているコマ」の判定自体が誤り、合格の判定がばらばらだと修得済み科目を正しく除けないため
  - UI を最後に置く。画面5は空きコマ検索の入口も含めて一度に作り直せるし、時間が足りなければ UI の範囲だけを削ればよい
- **Shared seams to watch**:
  - **移行 ↔ 不具合修正**：移行では既知の不具合もそのまま残す。例：`maxPeriods` の初期値 5、ピンを送らない、読み込み前の書き込み。直すのは `core-bug-fixes` で行う
  - **移行で作る部品の形**：移行で切り出す `utils/`（学期・クォーターの判定、セル探し、受講できる科目の絞り込み、合格の判定）、`hooks/`（Firestore 同期など）、`services/aiApi.ts` の形は、後続の3つの spec が全部使う。名前と引数は移行の design で決める
  - **不具合修正 ↔ data-model.md**：ピンを AI に送ると `TimetablePatternsRequest` の形が変わる。先に `data-model.md` を直す
  - **空きコマ検索 ↔ UI**：どちらも画面5（`GeneratorScreen`）を触る。空きコマ検索は「検索と追加の仕組みと、最低限の UI」を持つ。見た目の作り直しは UI の spec が持つ
  - **空きコマ検索 ↔ 時限の表示**：「空き」の判定は、`core-bug-fixes` で直した時限の範囲（何限まで見るか）と、クォーター（奇数Q・偶数Q）の分け方に従う

## Specs (dependency order)

- [ ] src-structure-migration -- `src/` を目標の構成へ移行する。必須はフォルダの移動と、後続の spec が使う部品（utils/・hooks/・services/aiApi.ts）の切り出し。余裕があれば lint ゼロと、それ以外の画面の整理。見た目と動きは変えない。Dependencies: none

- [ ] first-run-ux-refresh -- 画面の流れは保ったまま、画面3（科目選択）と画面5（生成）を初めての人でも迷わない形に作り直す。ほかの画面は説明文などの小さな改善にとどめる。Dependencies: src-structure-migration, empty-slot-search
