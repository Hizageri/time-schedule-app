# Brief: university-config

> 作成：2026-11-17。作者の決定で、もとの `university-data-model` を2つに分けたうちの1つ目（大学ごとの設定）。保存データの形は変えない。2つ目（データの形と移し替え）は `university-data-model`

## Problem

コマどりは全国の大学で使えることを目標にしている（`roadmap.md`）。ところが、大学ごとに違う値が、コードや初期値に会津大学のものとして直接入っている。

- 学期制（4学期制）、時限の数（11限）、成績の段階（A〜F とポイント）、科目の条件のビット（`target_bit`）の意味、大学名
- このまま次の spec（データの形・シラバスの DB 化・パターンのコード化）に進むと、どれも会津大学専用の前提の上に作ることになる

また、今のアプリの成績の段階の初期値（A=4・B=3・C=2・D=0・F=0）は、会津大学の実際の段階（D がない）と合っていない。

## Current State

- `src/config/universityConfig.ts` に会津大学の値（大学名、最後の時限 11、最大時限の下限 5）だけがある（`secure-and-stable` で1か所に集めた）
- 成績の段階は `userProfile.gradingScale`（初期値 A=4・B=3・C=2・D=0・F=0）、学期制は `userProfile.termSystem`（`'4学期制'`）として、利用者のデータに入っている
- `target_bit` の読み取り（学年・クォーター・学期・再履修のビットの意味）は `src/utils/targetBit.ts` に集まっていて、ほかのファイルから15か所で使われている
- 曜日（月〜土）や時限の並び、前期＝Q1/Q2・後期＝Q3/Q4 の決まりも、コードの中にある
- 会津大学の成績の段階（2026-11-17 作者より）：A（80 点以上）=4、B（65〜79 点）=3、C（50〜64 点）=2、F（50 点未満）=0。D はない

## Desired Outcome

- 大学ごとに違う値を、**大学ごとの設定**として持てる。会津大学は設定の1つになる
- 学期制・時限の数・成績の段階・`target_bit` の意味・大学名を使う計算と表示は、今の大学の設定から値を読む
- 会津大学の設定で、今までどおりの動き（共通の確認 1〜6）になる
- 試しの別の大学の設定（学期制・時限の数・成績の段階が違うもの）で、科目の絞り込み・時間割の表示・GPA の計算が設定どおりになる

## Scope

- **In**:
  - 大学ごとの設定の形と、会津大学の設定
  - 試しの別の大学の設定（確かめるためだけ。本物の他大学のデータは入れない）
  - 設定を読むように、計算と表示を直す（`target_bit` の読み取り、学期・クォーター、時限、成績の段階・GPA、大学名）
  - 会津大学の成績の段階を、実際のもの（D なし）にする
  - steering（`data-model.md`・`product.md`・`tech.md`・`structure.md`）の更新
- **Out**:
  - 利用者のデータの形と保存場所の変更、データの移し替え（`university-data-model`）
  - 利用者が大学を選ぶ画面（使えるのは会津大学だけのまま）
  - 本物の他大学のデータを集めて入れること
  - 見た目の変更

## Boundary Candidates

- 大学ごとの設定（形・会津大学の値・試しの大学の値）と、今の大学の設定を読む部品
- `target_bit` の読み取り（大学ごとの意味に合わせる）
- 学期・クォーター・時限・曜日の決まり
- 成績の段階と GPA の計算

## Out of Boundary

- 利用者のデータの形（大学 ID・科目 ID・学期ごとの保存）は `university-data-model` が持つ
- シラバスの置き場所は `syllabus-db` が持つ
- 時間割の組み合わせの計算は `timetable-pattern-engine` が持つ

## Upstream / Downstream

- **Upstream**：`data-model.md`（型の正）、`secure-and-stable`（大学ごとの値を1か所に集めた形）、`src-structure-migration`（`utils/targetBit.ts`・`config/` の形）、ADR-0005
- **Downstream**：`university-data-model`（大学 ID から設定を引く）、`timetable-pattern-engine`・`empty-slot-search`（時限・曜日・クォーターの決まりを使う）

## Constraints

- 保存データの形は変えない（データの移し替えは `university-data-model` で1回にまとめる）
- 型の正は `data-model.md`。設定の形を決めたら、先にこのファイルを直す
- 新しいライブラリはなるべく入れない。新しいコードで `any` を使わない

## Open Questions（要件で決める）

1. **今の利用者の成績の段階**：利用者のデータにすでに入っている `gradingScale`（D がある初期値）を、会津大学の実際の段階に変えるか。変える場合、この spec では保存データの形を変えないので、どう扱うか（例：保存データの値は残し、計算は大学の設定の段階を使う）
2. **D の成績が入っている利用者**：すでに D を入れた成績がある場合の扱い
