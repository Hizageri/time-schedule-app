# ADR-0002：Gemini はサーバー側（`api/`）からだけ呼ぶ

- 状態：採用
- 日付：2026-10-07（`CLAUDE.md` に記録）
- 関係する spec：`secure-and-stable`（AI 窓口の認証と入力の確認）
- 出典：`CLAUDE.md`「セキュリティ」、`.kiro/steering/tech.md`「環境変数」「技術上の決まり」、`.kiro/steering/deployment.md`「方針」「環境変数の保存場所」

## 背景

Gemini API は API キーで認証する。キーを持っている人は誰でも、こちらの利用料で Gemini を呼べる。Vite では `VITE_` で始まる環境変数がビルド時にクライアントのバンドルへ埋め込まれ、ブラウザの開発者ツールから誰でも読める。

## 選択肢

### 案A：ブラウザから Gemini を直接呼ぶ
- 概要：`VITE_GEMINI_API_KEY` のような変数にキーを入れ、React から SDK で呼ぶ
- メリット：サーバーが要らない。実装が短い
- デメリット：API キーがブラウザに公開される。キーを抜かれると第三者に使われ、利用料が請求される

### 案B：サーバー側の関数（Vercel Functions の `api/*.ts`）から呼ぶ
- 概要：ブラウザは `/api/consultation` などを呼び、サーバーがキーを使って Gemini を呼ぶ。キーは `GOOGLE_API_KEY`（`VITE_` なし）としてサーバーの環境変数にだけ置く
- メリット：キーがブラウザに出ない。サーバー側で認証（Firebase ID トークンの検証、ADR-0006）や入力の上限（`api/_lib/validation.ts`）をかけられる。プロンプトもサーバー側で組み立てるので、クライアントから書き換えられない
- デメリット：サーバーの関数を書いて保守する必要がある。1回の通信が増える

## 決めたこと

案B。

## 選ばなかった理由

- 案A：API キーという秘密情報がクライアントに露出する。これは `CLAUDE.md` で「`VITE_` から始まる変数に秘密情報を入れない」として禁止している

## 結果

- 良くなること：API キーが漏れない。サーバー側を「関所」にして、認証・入力の確認・科目の中身の引き直し（ADR-0007）をまとめて行える
- 受け入れたトレードオフ：`api/` のコードの保守。開発時は `vite.config.ts` の `local-api-handler` で `/api` を動かす仕組みが要る
- 見直す条件：記録なし
