# ADR-0015：利用者のデータ（`AppState`）を Firestore の `users/{uid}` 1ドキュメントにまるごと保存する

- 状態：採用（university-data-model で ADR-0016 に置きかえる予定）
- 日付：2026-10 以前（アプリを作り始めたとき）
- 関係する spec：なし（最初の技術選定）。保存の仕方は `secure-and-stable`（ADR-0008）、置きかえは `university-data-model`
- 出典：作者への聞き取り（2026-11-06）、`src/types/index.ts`、`src/hooks/useUserDataSync.ts`、`src/context/AppContext.tsx`（`startNewSemester`）、`firestore.rules`

## 背景

利用者ごとのデータ（プロフィール・設定・条件・選んだ科目・確定した時間割・成績・修得済み・ピン・教室名・今の画面）を、端末をまたいで保存する必要があった。Google でログインすると Firebase Authentication が利用者ごとの uid を発行するので、その uid でデータを結び付ける。

今の形：

- `AppState` を `users/{uid}` の1ドキュメントにまるごと書く（`setDoc`、`merge` なし。最後の変更から3秒後に1回。ADR-0008）
- `selectedCourses` にはシラバスの中身ごとコピーが入る（1科目あたり平均約 600B。上限 40 科目でも数十 KB で、Firestore の 1MB の上限には遠い）
- security rules：本人の `users/{uid}` だけ読み書きできる
- 「新学期へ進む」で、選んだ科目・確定した時間割・成績・ピン・教室名を消す。残るのはプロフィール・設定・修得済みの一覧（`earnedCredits`）

## 選択肢

### 案A：1ドキュメントにまるごと保存する
- 概要：上の今の形
- メリット：ログイン時の read は1回、保存の write は1回。1回の `setDoc` なので常に atomic。security rules が単純
- デメリット：小さな変更でも全体を書き直す。学期の履歴を残すと、ドキュメントが年々大きくなる

### 案B：利用者のドキュメントと、学期ごとのドキュメントに分ける
- 概要：`users/{uid}` と `users/{uid}/terms/{termId}`
- メリット：過去の学期を残せる。ふだんは今の学期だけを読み書きできる
- デメリット：複数のドキュメントを atomic に書くには batch write が要る。security rules に下の階層の match が要る

## 決めたこと

案A。

## 選ばなかった理由

- 案B：当時、比較して選んだわけではない。AI におすすめされた案A をそのまま採用した。特に理由はない（作者への聞き取り）

> 補足（記録にない技術的な説明）：履歴を残さず、1学期分だけを持つなら、データは数十 KB に収まるので、1ドキュメントで read・write の回数が最も少なくなる。最初の形としては単純で妥当だった

## 結果

- 良くなること：保存と読み込みが1か所で済む。ADR-0008 の「丸ごと書く」がそのまま使える
- 受け入れたトレードオフ：新学期へ進むと、前の学期の時間割と成績が消える。科目のコピーはシラバスを直しても古いまま（stale）になる
- 見直す条件：学期の履歴を残すとき、course-history を作るとき、全国展開で大学を ID で持つとき → ADR-0016
