# ADR-0013：シラバス・口コミを JSON ファイルとしてクライアントのバンドルに含める

- 状態：採用（全国展開のときに ADR-0014 で置きかえる予定）
- 日付：2026-10 以前（アプリを作り始めたとき）
- 関係する spec：なし（最初の技術選定）。置きかえは `syllabus-db`
- 出典：作者への聞き取り（2026-11-06）、`src/data/index.ts`、`api/_lib/syllabus.ts`、`vercel.json`、`.kiro/steering/structure.md`「データファイルの扱い」

## 背景

会津大学のシラバス（204科目）と先輩の口コミを、アプリで使う必要があった。作者にとって初めてのアプリ開発で、データの置き場所を AI に相談した。

今の形：

- `src/data/syllabus.json`・`reviews_bit.json`・`reviews_text.json` を `src/data/index.ts` で `import` して結合し、`MOCK_COURSES` を作る。クライアントの JS バンドルにまるごと入る（約 38KB gzip。バンドル全体 328KB の約 12%）
- サーバー（`api/_lib/syllabus.ts`）は同じ JSON を `fs` で読む。`vercel.json` の `includeFiles` で同梱する（ADR-0007）
- 更新の流れ：`syllabus.json` は手で直す。口コミは `raw_reviews.json` を直して `npm run build:reviews` で生成物を作る → commit → push → Vercel が再デプロイ

## 選択肢

### 案A：JSON をバンドルに含める
- 概要：上の今の形
- メリット：ネットワークの往復がない。コストがかからない。DB の設計や運用が要らない。データの変更が git の履歴に残り、diff でレビューでき、revert で戻せる
- デメリット：利用者が全科目分をダウンロードする。データの更新に再デプロイが要る

### 案B：DB（Firestore など）に入れる
- 概要：シラバスを DB に置き、必要な分だけ読む
- メリット：必要な分だけ読める。データの更新とデプロイを切り離せる
- デメリット：DB の設計、読み取りの課金、データを入れる仕組みが要る

## 決めたこと

案A。

## 選ばなかった理由

- 案B：当時、比較して選んだわけではない。AI に相談しておすすめされた案A をそのまま採用した。特にこだわりはない（作者への聞き取り）

> 補足（記録にない技術的な説明）：会津大学1校・204科目なら、バンドルに含めても約 38KB（gzip）で、初回の読み込みへの影響は小さい。最初の1校で動くものを作る段階では、DB を用意しない案A は妥当な選択だった

## 結果

- 良くなること：DB なしで、すぐにアプリを動かせた
- 受け入れたトレードオフ：全科目分のダウンロード。データの更新のたびに再デプロイ
- 見直す条件：全国展開（大学・年度が増える）→ ADR-0014

## 聞かれたときの答え方

> Q. シラバスのデータはどこに置いていますか？ なぜですか？

今は JSON ファイルにして、クライアントのバンドルに含めています。初めてのアプリ開発で、まず会津大学1校で動くものを作る段階だったので、DB を用意しない一番単純な形にしました。204科目で約 38KB（gzip）なので、1校なら問題になりません。ただ全国展開すると、全員が全大学分をダウンロードすることになるので、DB に移す予定です（ADR-0014）。

- よくある追加の質問：最初から DB にしなかったのはなぜですか？
  - 答え：（作者の言葉で書く。参考：当時は AI のおすすめをそのまま採用した。今振り返ると、1校の段階では DB の設計・課金・データ投入の仕組みが要らない分、案A のほうが早く作れた）
