# ADR-0012：画面の切り替えを URL ベースのルーティングにするか

- 状態：提案（未決定。`first-run-ux-refresh` を始める前に決める）

- 関係する spec：`first-run-ux-refresh`
- 出典：`.kiro/steering/roadmap.md`「着手する前に必ず決めること」、`.kiro/steering/tech.md`（ルーティング：なし）

## 背景

今は URL がずっと同じで、保存データの `currentScreen`（1〜8）を見て `src/App.tsx` の `ScreenManager` が画面を切り替えている。次の問題がある。

- ブラウザの「戻る」で、アプリの前の画面ではなく、コマどりを開く前のページに戻る。スマートフォンでは、戻るのジェスチャーでアプリから出てしまう
- 画面ごとの URL がないので、ブックマーク・共有ができず、画面ごとのアクセス解析もできない
- 空きコマ検索などで画面が増えると、番号だけでは分かりにくい

## 選択肢

### 案A：今のまま（状態による切り替え）
- 概要：`currentScreen` の値で画面を出し分ける
- メリット：パソコンで止めた画面の続きを、スマートフォンでもそのまま開ける（画面が Firestore に保存されている）。画面の順番（条件 → 科目選択 → 相談 → 生成）が崩れない
- デメリット：上の3つの問題が残る

### 案B：URL ベースのルーティング（React Router など）
- 概要：画面ごとに URL を持ち、History API で切り替える
- メリット：「戻る」が効く。ブックマーク・共有・画面ごとの計測ができる。Web の標準的なやり方
- デメリット：ルーターの依存が増える。URL と保存データの「今の画面」が食い違ったときの決まりが要る。URL を直接打ってオンボーディングなどを飛ばされないようにする（route guard）必要がある

## 決めたこと

まだ決めていない。決めること：案B に変えるか、案A のままにするか。変えるなら `first-run-ux-refresh` の範囲に入れるか、別の spec にするか。

## 結果

- この時期に決める理由：画面の作り直しと空きコマ検索で画面が増えるので、変える価値が大きく、作り直しと一緒にやれば手間も少ない
- `src-structure-migration` では「見た目と動きを変えない」ので変えていない
