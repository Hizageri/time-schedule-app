# ADR-0007：AI に渡す科目の中身は、送られた文章ではなくサーバーのシラバスから引く

- 状態：採用
- 日付：2026-10-23
- 関係する spec：`secure-and-stable`（要件 2）
- 出典：`.kiro/specs/secure-and-stable/research.md`「Architecture Pattern Evaluation」「Decision: 科目の中身はサーバーのシラバスから引く」、`.kiro/specs/secure-and-stable/design.md`

## 背景

ブラウザは AI 窓口に、科目オブジェクト（シラバスの概要などの本文を含む）をそのまま送っていた。要件 2 の目的は「大量のデータや壊れたデータで、Gemini の利用料が増えない」こと。クライアントから送られたデータは書き換えられる前提で考える必要がある。

## 選択肢

### 案A：送られた科目の文章をそのまま使い、上限だけかける
- 概要：今のまま。件数や文字数に上限をかける
- メリット：変更が小さい
- デメリット：概要などの長い文章を書き換えて送られると、そのまま AI のプロンプトに入る

### 案B：科目 ID だけを信じ、中身はサーバーのシラバスから引く
- 概要：送られた `id_name` で、サーバー側の `src/data/syllabus.json` を引いてプロンプトを作る。見つからない ID は 400
- メリット：プロンプトに入る科目の文章が、こちらのデータだけになる。上限は件数と ID の形だけで済む
- デメリット：サーバーがシラバスのファイルを読める必要がある（`vercel.json` の `includeFiles` で同梱）

## 決めたこと

案B。リクエストの形（科目オブジェクトの一覧）は互換のため変えず、サーバーが `id_name` 以外を使わない。

## 選ばなかった理由

- 案A：件数の上限だけでは、1件の中身を長くされると利用料を守れない。プロンプトに任意の文章を入れられる

## 結果

- 良くなること：利用料の上振れと、科目の文章を使ったプロンプトの書き換えを防げる
- 受け入れたトレードオフ：`includeFiles` の設定が要る。読めないときは 500 を返してログに残す（空の配列で黙って進めない）
- 残るリスク：プロフィールの文章（100 文字まで）はプロンプトに入るので、プロンプトの指示を書き換えようとする文章が入りうる。影響は本人への AI の返答だけで、ほかの利用者のデータや秘密情報には届かない（AI 窓口は Firestore に触らない）
- 見直す条件：第2段階の `syllabus-db` で、シラバスの読み込み先が DB に変わるとき

## 聞かれたときの答え方

> Q. クライアントから科目のデータを受け取っているのに、なぜサーバーで引き直すのですか？

クライアントから送られてくるデータは書き換えられる前提で考えています。科目の本文をそのまま使うと、長い文章を送られたときに Gemini の利用料が増えたり、プロンプトに任意の文章を入れられたりします。そこでサーバーは科目 ID だけを信じて、自分の持っているシラバスから中身を引き直してプロンプトを作っています。

- よくある追加の質問：ならリクエストを ID だけにすればよいのでは？
  - 答え：そのほうがきれいですが、この spec ではクライアントとの互換を保つためにリクエストの形は変えず、サーバーが ID 以外を使わない形にしました
