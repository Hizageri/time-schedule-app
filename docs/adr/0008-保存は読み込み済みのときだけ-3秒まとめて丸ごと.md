# ADR-0008：保存は「読み込み済みのときだけ・3秒の debounce・`merge` なしで丸ごと」

- 状態：採用
- 日付：2026-10-23
- 関係する spec：`secure-and-stable`（要件 5・6・7）、`src-structure-migration`（`hooks/useUserDataSync.ts` に分けた。動きは変えていない）
- 出典：`.kiro/specs/secure-and-stable/research.md`「Architecture Pattern Evaluation」「Decision: 保存は…」「Risks & Mitigations」、`.kiro/steering/tech.md`「アーキテクチャ」「既知の技術的な注意点」

## 背景

状態（`AppState`）は Firestore の `users/{uid}` の1ドキュメントに保存している。次の3つの不具合があった。

- 上書き：ログイン直後、読み込みが終わる前に初期値（`defaultState`）が保存され、保存していた時間割が消える
- 復活：`merge: true` で書いていたので、消したキー（ピンなど）がドキュメントに残り、リロードで戻る
- 回数：変更のたびに書き込んでいた

## 選択肢

### 案A：`merge: true` のまま、消したキーに削除の印（`deleteField()`）を付ける
- 概要：消す処理のたびに、そのキーの削除を書く
- メリット：部分の書き込みで済む
- デメリット：消す場所すべてで削除の印が必要。1か所でも漏れると復活する

### 案B：読み込みが終わってから、`merge` なしで状態を丸ごと書く
- 概要：読み込みの状態（`loadStatus`：`signedOut`・`loading`・`ready`・`error`）を持ち、`ready` のときだけ保存を予約する。予約は最後の変更から3秒後に1回（debounce）、`setDoc` を `merge` なしで書く。ページが隠れる・閉じられる（`visibilitychange` の hidden、`pagehide`）・ログアウトの前・利用者が切り替わる前は、待っている保存をすぐ書く。予約には「どの利用者の保存か」を持たせる
- メリット：ドキュメントが常に状態そのものになり、消したものは自動で消える。上書き・復活・回数の3つを保存の入口1か所で解決できる
- デメリット：読み込み前に1回でも書くと全部消える。読み込みが終わるまで書かない仕組みが必須

## 決めたこと

案B。

## 選ばなかった理由

- 案A：削除の印を付ける場所が散らばり、漏れやすい。漏れは「消したものが戻る」という気づきにくい不具合になる

## 結果

- 良くなること：保存のルールが1か所にまとまる。読み込みに失敗したら保存を止め、再読み込みの画面を出すので、壊れたデータで上書きしない
- 受け入れたトレードオフ：
  - 複数のタブで同時に編集すると、後から保存したほうが勝つ（last write wins）
  - ページが強制終了したときは、最後の3秒の変更が失われることがある
  - ページを閉じる瞬間の保存は、ブラウザが待たないことがある（要件は「試みる」）
  - `selectedCourses` にシラバス本文ごと入るので、ドキュメントが大きい（第2段階で ID だけにする予定）
- 見直す条件：複数端末の同時編集が必要になったとき、ドキュメントのサイズが問題になったとき
