# ADR-0005：全国展開を前提にし、大学ごとに変わる値を1か所の設定にする

- 状態：採用
- 日付：2026-10-22（方針）、2026-10-23（`universityConfig` の設計）、2026-10-30（`config/` に配置）
- 関係する spec：`secure-and-stable`、`src-structure-migration`、`university-data-model`（第2段階、これから）
- 出典：`.kiro/steering/roadmap.md`「Overview」「Constraints」、`.kiro/specs/secure-and-stable/research.md`「Decision: 大学ごとに変わる値は1か所の設定にする」、`.kiro/specs/src-structure-migration/research.md`「Decision: 設定は config/ に置く」

## 背景

今は会津大学だけで使うが、目標の1つは全国の大学で使えること。大学によって、学期制（会津大学は4学期制）・成績の段階（A〜F）・時限の数（11限）・科目の条件のビットの意味が違う。会津大学専用に直書きしたほうが楽な場面が多い。

## 選択肢

### 案A：今の大学の値を1か所の設定から渡す
- 概要：`src/config/universityConfig.ts` に会津大学の値（最後の時限 11、最大時限の下限 5）を置き、使う場所は設定から読む。成績の段階は `userProfile.gradingScale` から読む
- メリット：第2段階の `university-data-model` で、設定を大学ごとに切り替える形に置きかえやすい
- デメリット：今は大学が1つなのに、間接参照が1段増える

### 案B：会津大学の値をコードに直書きする
- 概要：`11` や `'A'` をそのまま書く
- メリット：今は最も簡単
- デメリット：全国展開のときに、散らばった直書きを探して直す必要がある。漏れやすい

### 案C：最初から複数の大学の設定を持てる仕組みを作る
- 概要：大学の一覧と、大学ごとの設定の読み込みまで作る
- メリット：全国展開の準備が一度に終わる
- デメリット：まだ使わない項目まで先回りして作ることになる（YAGNI）

## 決めたこと

案A。項目は今使うもの（最後の時限・最大時限の下限）だけにした。

## 選ばなかった理由

- 案B：「会津大学専用のほうが楽な場面でも、全国展開で困らないほうを選ぶ」という roadmap の方針に反する
- 案C：今は大学が1つで、項目を先回りして増やさない（secure-and-stable の「単純化」）。仕組みは第2段階の `university-data-model` で作る

## 結果

- 良くなること：大学ごとに変わる値を直す場所が1つになる。src-structure-migration では、学期・クォーターのビット判定も `utils/targetBit.ts` 1か所に集めたので、ビットの意味を大学ごとにするときの修正も1か所で済む
- 受け入れたトレードオフ：今は1大学なので、設定を経由する分だけ少し遠回り
- 見直す条件：`university-data-model` で大学ごとの設定に置きかえるとき
