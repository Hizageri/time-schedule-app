# ADR-0014：シラバス・口コミを DB に移し、必要な分だけ読む

- 状態：提案（`syllabus-db` の設計で決める）
- 日付：2026-11-06（論点と比較を記録）
- 関係する spec：`university-data-model`（科目 ID の付け方）、`syllabus-db`
- 出典：作者への聞き取り（2026-11-06）、`.kiro/steering/roadmap.md`（`syllabus-db`・Boundary Strategy）、ADR-0006・ADR-0007・ADR-0013

## 背景

ADR-0013 の形（JSON をバンドルに含める）は、全国展開で次の問題が出る。

- 作者の理由：全国展開したとき、JSON にまとめるやり方では、利用者が自分に要らない大学の情報までダウンロードし、アプリが重くなる（作者への聞き取り）
  - 規模の目安：今は1校で約 38KB（gzip）。日本の大学はおよそ 800 校あり、年度ごとにも残すと、同じ形のままでは数十 MB になる
- 作者の理由：大学が増えると、データの更新のたびにアプリの再デプロイが必要になる。データとアプリのリリースを切り離したい（作者への聞き取り）
  - 1校なら、シラバスの更新は年に1〜2回で、git の diff・revert・レビューが使えるので負担は小さい。負担が大きくなるのは、大学が増えたとき、開発者以外がデータを直すとき、利用者が口コミを投稿する機能を作るとき
- roadmap の理由：シラバスを大学ごと・年度ごとに持ち、過去の学期の科目も科目 ID（例：`u-aizu/2026/HS01`）で引けるようにする

科目の中身の内訳（gzip 後）：

- 一覧・時間割の計算に使う項目（`id_name`・`target_bit`・`credits`・`classes`）：約 5KB
- 詳細モーダルだけで使う項目（`outline`・`grading`）：約 24KB

## 選択肢

### 案A：今のまま（ADR-0013）
- メリット：単純。コストなし。git で管理できる
- デメリット：大学・年度が増えるほどバンドルが大きくなる。更新に再デプロイが要る
- 要件との適合：1校なら問題ない。全国展開・年度ごとの保存に合わない

### 案B：Firestore にシラバスのコレクションを作る
- 概要：例として `universities/{univId}/years/{year}/courses/{courseId}`
- メリット：今の Firebase の中で済み、新しいサービスが増えない。security rules で「誰でも読めるが書けない」にできる。大学・年度ごとに必要な分だけ読める。更新をデプロイから切り離せる
- デメリット：read はドキュメント単位で課金される（1科目1ドキュメントだと起動のたびに 204 read）。全文検索や複雑な検索はできない
- 対策：一覧用の項目を、大学・年度ごとに1ドキュメントにまとめる（上限 1MB に収まる）と 1 read で済む
- 要件との適合：高い

### 案C：RDB（Supabase の Postgres など）
- メリット：正規化して JOIN や全文検索ができる。空きコマ検索の条件を SQL で書ける
- デメリット：新しいサービスが増え、運用・課金・Firebase Auth との連携の手間が増える。roadmap の「新しいライブラリはなるべく入れない」に反する
- 要件との適合：機能は高いが、一人開発の今の規模では過剰。候補の計算はコードで行う（ADR-0001）ので、DB の検索機能の利点が小さい

### 案D：大学・年度ごとに分けた静的 JSON を、必要なときに fetch する
- 概要：例として `/data/u-aizu/2026/courses.json` を CDN（Vercel の静的ファイルや Cloud Storage）に置く
- メリット：DB が要らない。CDN のキャッシュで速い。自分の大学の分だけダウンロードできる
- デメリット：リポジトリに置くなら更新に再デプロイが要るまま（Cloud Storage なら不要）。検索できない
- 要件との適合：中くらい

### 別の軸：一覧と詳細を分ける（list / detail の分割）

- 一覧（約 5KB）は起動時に大学・年度ごとにまとめて読み、絞り込み・時間割の生成・空きコマ検索に使う
- 詳細（`outline`・`grading`・口コミの本文）は、詳細モーダルを開いたときにその科目の分だけ読む
- 案B でも案D でもできる。最初に読む量が約 1/6 になる

## 決めたこと

まだ決めていない。Claude の推奨は **案B ＋ list / detail の分割**（今の Firebase の中で済む・大学と年度ごとに持てる・更新をデプロイから切り離せる・一覧を1ドキュメントにすれば 1 read）。

`syllabus-db` の設計で決める。DB の形は `university-data-model` で決める科目 ID の付け方に依存するため（roadmap の Boundary Strategy）。
