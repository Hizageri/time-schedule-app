# ADR-0011：単体テストの代わりに、Playwright で本物の画面を動かす試しの画面（`checks/ui/`）を使う

- 状態：採用
- 日付：2026-10-30（リポジトリに入れた。第1段階では作業環境の一時フォルダで使っていた）
- 関係する spec：`src-structure-migration`（要件 5）、`secure-and-stable`・`student-period`（使い捨ての試しの画面で確認）
- 出典：`.kiro/specs/src-structure-migration/research.md`「試しの画面をリポジトリに入れる方法」「Decision: 試しの画面は本物の入口を読み込む」、`.kiro/specs/src-structure-migration/brief.md`、`.kiro/steering/tech.md`「試しの画面」

## 背景

テストの仕組みがなく、確認は手で行っていた（`roadmap.md`「確認の方法」）。src-structure-migration は「見た目と動きを1つも変えない」ことが条件なので、移行の前後で同じ確認を何度も機械的に流す必要があった。第1段階では、Firebase を偽物に差し替えて本物の画面を Playwright で動かす使い捨ての仕組みを作って確かめていた。

## 選択肢

### 案A：試しの画面をリポジトリに入れる（Vite ＋ Playwright、本物の入口を読み込む）
- 概要：Vite の `resolveId` で `firebase/auth`・`firebase/firestore`・`src/lib/firebase` を mock に差し替え、本物の入口 `src/main.tsx`（`StrictMode` あり）を開く。`/api/*` はシナリオごとに Playwright で mock し、`localhost` 以外への通信は止める。動きの確認に加えて、11 画面 × 2 幅の HTML を基準と比べる。`npm run check:ui` で流す
- メリット：import の名前で差し替えるので、ファイルの場所が変わっても同じ確認を流せる（移行の前後の比較に使える）。本物の画面と状態の流れをそのまま確かめられる。本物の Firebase・Gemini・`.env` を使わない
- デメリット：1回に 3〜5 分かかる。画面の HTML の比較は、見た目を変える spec では基準の作り直しが要る

### 案B：手による確認だけ
- 概要：今までどおり `roadmap.md` の共通の確認 1〜6 を手で行う
- メリット：仕組みがいらない
- デメリット：移行のように細かい段階ごとに何度も確かめる作業では、時間がかかり、見落としも出る

> 補足（記録にない比較）：ほかに、Vitest などの単体テスト（関数ごと）や、本物の Firebase のエミュレーターを使う方法もある。記録には比較が書かれていない。単体テストは関数の正しさは確かめられるが、移行で起きやすい「import の付け替えで画面が壊れる」ことは確かめにくい

## 決めたこと

案A（`checks/ui/`）。`src/` の外に置き、本番のビルドに入れない。本物の入口を読み込む形にした。

## 選ばなかった理由

- 案B：「動きを1つも変えない」を、段階ごとに何度も確かめるのには向かない
- 試しの画面を `components/App` から直接読む形（第1段階のやり方）：移行で `App.tsx` の場所が変わると、試しの画面も直す必要がある。本物の入口なら移行の前後で同じに流せる

## 結果

- 良くなること：移行の前のコードで 122 件を通してから移し、各タスクの後に同じ 122 件を通して、動きが同じことを確かめられた。本番のビルドに mock が入っていないことも確かめている
- 受け入れたトレードオフ：1回の実行時間。作者のパソコンでは最初に1回 `npx playwright install chromium` が要る。本物の Firebase・Gemini・本番の URL での確認は、引き続き作者が手で行う
- 見直す条件：記録なし

## 聞かれたときの答え方

> Q. テストはどうしているのですか？

単体テストの仕組みはまだありませんが、本物の画面を Playwright で動かす E2E に近い確認を `npm run check:ui` で流しています。Firebase は Vite の `resolveId` で mock に差し替え、AI の窓口は Playwright でリクエストを差し替えるので、本物のサービスや API キーは使いません。保存の debounce や AI の 401 の扱いなどの動き 100 件と、11 画面 × 2 幅の HTML の比較 22 件を確かめていて、フォルダ構成の移行のときは、この 122 件が移行の前後で同じに通ることを条件にしました。
